\section{Introduction}

Large Language Models  are increasingly integrated into software development to automate code generation, testing  and user interface implementation. LLM based coding agents can interpret the natural language requirements and generate the web applications with less human intervention. Ensuring the accessibility in LLM generated interfaces remains a challenge, as applications satisfy requirements while containing barriers that affect users who rely on keyboard navigation, screen readers, and other assistive technologies \cite{aljedaani2024}. 

Web accessibility is an essential aspect of software quality, ensuring that applications can be accessed and operated by individuals with diverse abilities. The web accessibility standards such as the Web Content Accessibility Guidelines (WCAG) 2.2 and the WAI- ARIA Authoring Practices Guide (APG) provide guidelines for accessible development for commonly used interface components \cite{wcag2022,apg2026}. LLM coding agents may produce interfaces with inadequate semantic structures, missing accessible labels, incomplete keyboard interactions, or improper focus management \cite{aljedaani2024,gurita2025}. This highlights the development approaches that incorporates the accessibility considerations into LLM-assisted software engineering.

This study, titled \emph{An Empirical Study of Test-Driven Development and Accessibility Prompting in LLM-Generated Web Interfaces}, investigates how Test-Driven Development (TDD) and accessibility instructions influence the accessibility of web interfaces generated by LLM coding agents. This research examines whether test-first development can guide coding agents toward implementing accessibility requirements during test generation or during implementation influences the outcomes of the results. Additionally, the study also investigates which accessibility requirements does LLM coding agents satisfy consistently and which may also seem challenging. Through these mentioned investigations, the research aims to identify the development practices that support more accessible and reliable LLM- generated web application.

The primary contributions of this study are: 
\begin{itemize}
  \item \textbf{Improving accessibility through TDD :} Comparing test-first development with direct code generation to understand how TDD affects the accessibility of LLM-generated web interfaces.
  \item \textbf{Impact of accessibility instructions :} Examining whether asking LLM coding agents to follow WCAG 2.2 AA and APG guidelines improves the accessibility of generated web interfaces.
  \item \textbf{Comparing accessibility instructions in Red and Green phases :} Evaluating whether providing accessibility instructions during test generation (Red phase) or test implementation (Green Phase) provides better accessibility results.
  \item \textbf{Evaluation of development efficiency : }Comparing the accessibility results and output token usage of different development approaches to understand their efficiency.
\end{itemize}

\section{Background}

\subsection{Web accessibility and WCAG 2.2:}

Web accessibility refers to the design and development of web applications that can be accessed, understood, and operated by individuals with diverse abilities. The Web Content Accessibility Guidelines (WCAG), developed by the World Wide Web Consortium (W3C), establish internationally recognized recommendations for improving accessibility. WCAG 2.2 is organized around four fundamental principles: Perceivable, Operable, Understandable, and Robust (POUR)\cite{wcag2022}. These principles ensure that information is presented in accessible formats, interface components can be operated through different input methods, content and navigation are understandable, and applications remain compatible with assistive technologies.

WCAG 2.2 defines the success criteria categorized into three conformance levels : A, AA, AAA\cite{wcag2022}. The level AA is the commonly adopted category for accessible web development because it addresses the important accessibility barriers. Most relevant requirements include keyboard accessibility, visible focus indicators, sufficient colour contrast, accessible names, and predictable navigation. In this study, WCAG 2.2 Level AA serves as the primary accessibility standard for evaluating the interfaces generated by LLM coding agents. Its success criteria provide a consistent basis for determining whether generated applications satisfy the provided accessibility requirements.

\subsection{WAI-ARIA  Authoring Practices Guide (APG):}

The WAI-ARIA Authoring Practices Guide provides the practical recommendations for the implementation of accessible interface components using Accessible Rich Internet Applications (ARIA), HTML, and JavaScript \cite{apg2026}.  While WCAG defines the recognised accessibility requirements , APG defines the recognised design patterns and interaction behaviours for common user interface components that includes dialogs, accordions, carousels, tabs, radio groups, and comboboxes\cite{apg2026}.

For example, an accessible modal dialog should allow users to navigate using a keyboard, close it using the Escape key, and prevent interaction with the background while it is open. Similarly, tabs and selection controls should support keyboard navigation and clearly indicate the selected option \cite{apg2026}. Using correct ARIA attributes alone is not enough, as interface components must also function properly when users interact with them. In this project, the Trail Runner 2 product page includes 13 functional features based on APG patterns. These features help evaluate whether LLM-generated interfaces are accessible and work efficiently for users.

\subsection{Test-Driven Development:}

Test-Driven Development (TDD) is a software development approach where tests are written before writing the actual code. TDD follows three main stages: Red, Green, and Refactor \cite{mathews2024}. In the Red phase, developers write tests for the expected functions of the application, which initially fail because the code has not yet been developed. In the Green phase, the code is written to make these tests pass. Finally, in the Refactor phase, the code is improved without changing its functionality.

TDD uses tests to clearly define how an application should work, making the requirements easier to understand. When accessibility requirements are included in these tests, they help ensure that features such as keyboard navigation, focus management, and interactive components work correctly\cite{fakhoury2024}. In this research, LLM coding agents follow a two-step TDD process. First, generating Playwright tests during the Red phase, and then develop the application during the Green phase. The study compares whether providing accessibility instructions during the Red or Green phase affects the accessibility of the generated web interfaces.

\subsection{LLM Based Coding Agents:}

Large Language Models (LLMs) are trained using large amounts of text and programming code, which helps them understand software requirements and generate code from natural language instructions. LLM-based coding agents use these models along with development tools to create and modify files, run commands, manage software dependencies, and test applications. Unlike traditional code completion tools, coding agents can perform several development tasks independently and use test results to identify and fix errors.

However, LLM coding agents may generate applications that work correctly but do not fully meet accessibility requirements \cite{suh2025}. This means that an application can perform its intended functions while still being difficult for users with disabilities to access or use. In this study, two LLMs, Claude Haiku and GLM 5.3, use the Claude Code framework to develop the same web interface under different conditions. The project examines whether providing clear accessibility instructions or using Test-Driven Development (TDD) helps these agents generate more accessible web applications.

\subsection{Accessibility Testing Approaches:}

Accessibility testing is the process of checking whether web applications follow accessibility standards and can be used by people who depend on assistive technologies. Automated testing tools help identify common accessibility issues, such as missing labels, incorrect ARIA attributes, and errors in page structure. Tools like ESLint with the jsx-a11y plugin \cite{eslintA11y} check React code for accessibility issues, while axe-core \cite{axe2026} checks web pages for accessibility violations. Playwright \cite{playwright2026} is used to test how users interact with web applications, including keyboard navigation, component functionality, and keyboard focus.

However, automated tools cannot detect all accessibility problems. Some issues, such as difficult keyboard interactions, unclear descriptions, and incorrect focus behaviour, require manual testing. Therefore, combining automated and manual testing helps provide a more complete evaluation of web accessibility \cite{playwright2026}. In this project, both methods are used to evaluate the generated web interfaces through 90 accessibility checks, including 39 automated checks and 51 manual checks, based on WCAG 2.2 Level AA and APG guidelines.

\section{Methodology}

To find out whether TDD helps LLM coding agents build accessible user interfaces, we ran a controlled experiment. An agent built the same web page from the same requirements many times, and only the prompt changed between runs. Two factors were varied in the prompt. The first is the development process, either building the page directly or following Test-Driven Development (TDD). The second is whether the prompt asks for accessibility. Everything else was kept the same in every run, including the requirements, the starting code, the tools and the environment, so any difference in the result can be traced back to the prompt.

The two factors produce five conditions, and each condition ran twice with each of two models, for 20 runs in total. Every finished page was then scored against the same accessibility checks. The rest of this section describes the task given to the agent, the five conditions and their prompts, the models, how the agent was run in isolation, and the metrics used to compare the results.

The features are written from the shopper's point of view and never mention accessibility, so the only accessibility signal the agent receives comes from the prompt. Every run starts from the same empty React app.

\subsection{Conditions}

The study compares five conditions (Table~\ref{tab:conditions}). They differ in the development process:
\begin{itemize}
  \item \textbf{Baseline} conditions use a single prompt that asks the agent to build the page.
  \item \textbf{TDD} conditions use two prompts in two separate sessions.
  \begin{itemize}
    \item \textbf{Red phase.} The agent only writes Playwright tests for the requirements and leaves the page empty.
    \item \textbf{Green phase.} The agent builds the page, and the existing tests must pass.
  \end{itemize}
\end{itemize}

They also differ in whether the prompt asks for accessibility (Fig.~\ref{fig:prompts}):
\begin{itemize}
  \item \textbf{Agnostic} prompts never mention accessibility.
  \item \textbf{Oriented} prompts add one sentence that asks for WCAG 2.2 AA and the APG. The sentence does not name any technique, such as keyboard support or focus handling, so the agent has to decide what accessibility means for each feature.
\end{itemize}

In the TDD conditions, the accessibility sentence can go in either session:
\begin{itemize}
  \item \textbf{tdd-oriented} puts it in the Red phase, so the agent must write tests that check accessibility.
  \item \textbf{tdd-green-oriented} puts it in the Green phase, so the agent writes plain feature tests and is asked for accessibility only while building the page.
\end{itemize}

Each research question maps to one comparison between conditions:
\begin{itemize}
  \item \textbf{RQ1.} Baseline against TDD across all five conditions shows whether TDD helps.
  \item \textbf{RQ2.} Baseline and TDD with accessibility in Red show how much the accessibility sentence matters.
  \item \textbf{RQ3.} Tdd-oriented against tdd-green-oriented shows whether the sentence works better in the tests or in the implementation.
  \item \textbf{RQ4.} Results by component show which accessibility requirements are reliable.
  \item \textbf{RQ5.} Score per 10{,}000 output tokens compares efficiency.

\subsection{Models and runs}

Two models of different cost and reasoning ability ran through the Claude Code command-line agent (version 2.1.309):
\begin{itemize}
  \item \textbf{Claude Haiku}, a small low-cost model.
  \item \textbf{GLM~5.3}, a large reasoning model.
\end{itemize}
Both ran with Claude Code's default reasoning settings, with extended thinking enabled and no effort level set by hand, so each model reasons as much as the agent normally lets it. Each condition ran twice with each model, which gives 5 conditions $\times$ 2 models $\times$ 2 runs $=$ 20 runs. Each run is saved as its own git branch, with one commit per session.

\subsection{Running the agent}

Each session runs in a new Docker container that is deleted afterwards. The container only sees a fresh copy of the app. It cannot see the other conditions, the other runs, or the evaluation code. The agent starts with no saved settings, memories, plugins or past chats, and every container has Node.js, git, Playwright browsers and Claude Code installed. The agent works on its own, with no human help. When a session ends, a script commits whatever the agent left, and the model, prompts, token usage, time and full transcript are logged.

\subsection{Metrics}

Every finished page is checked against 90 accessibility checks based on WCAG 2.2 AA and the APG, described in Section~\ref{sec:evaluation}. Each check covers one behaviour, for example ``Escape closes the size guide'', and ends as \emph{pass}, \emph{fail} or \emph{skip}. Of the 90 checks, 39 are automated and 51 are done by hand. A check is skipped only when it cannot be judged, and skipped checks are left out of every metric. Each check is also tagged with the WCAG success criterion it tests, or as an APG convention when no criterion applies.

\textbf{Accessibility score.} The share of judged checks that pass:
\begin{equation}
  \text{Score} = 100 \times \frac{\text{passed}}{\text{passed} + \text{failed}}.
\end{equation}
For a run, \textit{passed} and \textit{failed} count its own checks. For a condition, they add up the checks of all its runs, so every judged check counts the same.

\textbf{Keyboard task completion.} Whether a keyboard-only user can buy the shoe. The user must be able to pick a color, open the size list and pick a size, and type a quantity, all without getting trapped. A run scores 1 if every step works and 0 otherwise.

\textbf{Failed WCAG success criteria.} WCAG judges conformance per success criterion, and a criterion fails if any part of the page fails it. This metric counts the different criteria with at least one failed check.

\textbf{APG widget conformance.} The number of the ten APG widgets, from the breadcrumb to the accordion, with no failed check. Each widget counts once, so a widget with many checks, such as the size list, does not dominate the result.

\textbf{Severity-weighted score.} Not every failure hurts users the same. A failure is a \emph{blocker} when a feature cannot be used by keyboard (WCAG 2.1.1 or 2.1.2), \emph{serious} for any other WCAG failure, and \emph{minor} for a missing APG convention. First, the weighted failure percentage $f$ is calculated:
\begin{equation}
  f = 100 \times \frac{3 \times \text{blockers} + 2 \times \text{serious} + \text{minor}}{\text{maximum possible weight of judged checks}}.
\end{equation}
The weighted score is then:
\begin{equation}
  \text{Weighted score} = 100 - f.
\end{equation}

\textbf{Token efficiency.} The accessibility score per 10{,}000 output tokens:
\begin{equation}
  \text{Efficiency} = \frac{\text{Score}}{\text{output tokens} / 10{,}000}.
\end{equation}
The charts show 95\% bootstrap intervals based on 10{,}000 resamples of the runs.

\subsection{RQ2: How much does explicitly asking for accessibility (WCAG 2.2 AA and APG) change the outcome, compared with the development process?}

Looking at the results of the runs from the perspective of the checks
(Fig \ref{fig:rq4-failures}), all of the checks that the \textit{agnostic}
runs failed were improved in the \textit{oriented} runs, with the exception of "tooltip
hover persistence". Tooltip hover persistence is an accessibility criterion
which states that the information presented by the tooltip must remain
visible when the user hovers their mouse above it, and it must only 
disappear when the mouse is moved away, the "escape" key is 
engaged, or the information is no longer valid \cite{w3c2026hover}. The \textit{oriented}
runs failed this check more than the \textit{agnostic} runs by roughly 10\%.
It is possible that certain accessibility rules were overlooked by the LLMs

\section{Threats to Validity}

\subsection{Construct Validity}

\begin{itemize}
  \item \textbf{Checklist design.} One author created the checklist, linked each check to WCAG and set its severity. These choices may affect the scores. To reduce this risk, the checklist follows WCAG 2.2 AA and the APG, and every run uses the same final checklist.
  \item \textbf{Accessibility versus usability.} Passing the checklist does not mean that a page is usable by everyone. The study used automated tools and keyboard tests, but no screen readers or users with disabilities.
\end{itemize}

\subsection{Internal Validity}

\begin{itemize}
  \item \textbf{Unblinded evaluation.} Only one evaluation was executed and the evaluator knew each run's condition. Future work should hide the conditions and use more raters.
  \item \textbf{Model configuration.} The models used different providers, and Claude Code controlled their reasoning settings. These differences may affect the results so it is not possible to directly compare reasoning ability.
\end{itemize}

\subsection{External Validity}

\begin{itemize}
  \item \textbf{One task.} This experiment used one React product page with 13 APG-based features. The findings may not apply to other interfaces, domains or frameworks.
  \item \textbf{Two models and one coding agent.} This study tested only Claude Haiku and GLM~5.3 through Claude Code. Other models and coding agents may behave differently.
  \item \textbf{Prompt-based TDD.} An LLM followed two TDD prompts and wrote a small test suite. Human-written tests, larger suites or another TDD process may give different results.
  \item \textbf{Short accessibility instruction.} The oriented prompts used one sentence asking for WCAG 2.2 AA and APG compliance. More detailed requirements like examples or design-system guidance may improve the results.
\end{itemize}

\section{Related Work}

Several studies have examined accessibility issues in web applications generated by Large Language Models. Aljedaani et al.\cite{aljedaani2024} studied that the websites generated by ChatGPT often contained accessibility issues that includes missing labels, poor color contrast and missing alternative text. Their study also examined the ability to fix the accessibility issues in the ChatGPT generated codes.This study highlights the importance of evaluating the accessibility of LLM-generated applications.

Guriță and Vatavu \cite{gurita2025} compared accessibility-agnoistic and accessibility-oriented prompts used for web interfaces generation in their research. Their research also highlights that providing accessibility instructions with a clear and meaningful assertions reduced the accessibility violations however some issue still remained. Similarly Suh et al. \cite{suh2025} compared code written by human with the LLM-generated code and also introduced FeedA11y which is a feedback-based approach to improve accessibility. These studies show that providing clear prompt strategies and feedbacks of the previous runs can influence the accessibility of the code.

Studies have also examined the use of Test-Driven Development to improve the code generation with Large Language Models(LLM).Mathews and Nagappan \cite{mathews2024} experimented that providing LLM with the test cases along with the programming requirements generated better code which satisfied the functional requirements. Fakhoury et al. \cite{fakhoury2024} introduced an approach, TiCoder, which uses test to evaluate the LLM generated code and clarify the user requirements.These studies show that how tests can guide the code generation through LLM and provide more accurate implementations.  

The findings of the above mentioned studies provide both accessibility instructions and test based development can influence the quality of LLM-generated code.Guriță and Vatavu \cite{gurita2025} showed that providing clear accessibility instructions are important whereas Mathews and Nagappan \cite{mathews2024} and Fakhoury et al. \cite{fakhoury2024} highlight how test can help LLMs in generating the code that meets the software requirements.However, these studies have been studied independently. Providing an approach that combines accessibility instructions along with TDD to help the coding agents in considering the accessibility requirements in the development process. This provides a strong motivation in investigating whether providing accessibility instructions during test generation or code implementation provides better results.

Although prior works investigated the accessibility issues, prompting strategies and test-driven code generation however, the use of TDD specifically to improve web accessibility remains less explored.Most of the existing research focuses on accessibility prompting and functional correctness separately. This study combines both these research areas by comparing the code generation with TDD and also examining how accessibility instructions provided during Red or Green phase influences the accessibility of LLM-generated web interfaces.

\section{Future Work}

Several directions would strengthen and extend these results:
\begin{itemize}
  \item \textbf{More runs and models.} Each condition ran only twice per model, which is too few to test for significance. More runs per condition, and models at other points on the cost and reasoning scale, such as a frontier model at a high reasoning level, would show whether the small drop in score with TDD is real and whether it depends on the model.
  \item \textbf{Blinded evaluation with more raters.} The manual checks were done by one evaluator who knew the condition of each run. Repeating them with the branch names hidden and with a second rater, and reporting the agreement between raters, would remove the main threat to validity.
  \item \textbf{Other pages and applications.} This study used one product page with 13 features. Repeating it with other kinds of interfaces, such as long forms, dashboards or data tables, and with other frameworks would show whether the findings hold beyond this task.
  \item \textbf{Visual and functional quality.} Pages built with TDD sometimes looked worse, even when they were accessible. Measuring visual quality, for example with an LLM judge that scores screenshots against a fixed rubric, and functional correctness with a separate test suite, would show whether TDD trades away quality in ways this study did not capture.
\end{itemize}

\section{Conclusion}

This study investigated how Test-Driven Development and the accessibility instructions can influence the accessibility of web interfaces generated by LLM coding agents. This experiment compared the direct generated code with TDD- based development with five experimental conditions. The generated web interfaces were evaluated using the WCAG 2.2 Level AA and WAI-ARIA Authoring Practices Guide (APG) requirements. The objective of this study was to understand the combination of TDD and accessibility prompts guide LLM coding agents in generating more accessible web applications.

The results showed that the accessibility prompts improved the quality of generated interfaces, with the baseline-oriented condition amongst the five conditions achieved the highest accessibility score. Providing accessibility instructions during Red or Green phase provided similar results, which showcases that instruction placements had limited impact.The study also identified challenges in interactive components, mainly in price tooltips and size-selection controls. The direct code generation was token efficient than TDD-based approaches.The findings show that with the clearer accessibility instructions and proper testing help LLMs in creating more accessible web applications, while TDD did not show any additional improvements in this experiment.Future work could explore more advanced accessibility tests, different LLM coding agents, and more complex web applications to investigate whether TDD can improve accessibility outcomes across a wider range of development scenarios.
