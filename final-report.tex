\section{Methodology}

LLM coding agents built the same web page many times. Two factors changed between runs: whether the agent followed Test-Driven Development (TDD), and whether the prompt asked for accessibility. Each finished page was then scored for accessibility.

\subsection{The task}

We built a product page for a fictional trail running shoe, \emph{Trail Runner 2}, and wrote its requirements as 13 features. Each feature matches a standard component of the WAI-ARIA Authoring Practices Guide (APG), so every page exercises the same set of accessibility patterns (Table~\ref{tab:features}). The features are written from the shopper's point of view and never mention accessibility, so the only accessibility signal the agent receives comes from the prompt. Every run starts from the same empty React app.

\subsection{Conditions}

The study compares five conditions (Table~\ref{tab:conditions}). The \emph{baseline} conditions use one prompt: build the page. The \emph{TDD} conditions use two prompts in two separate sessions. In the first session (the Red phase), the agent only writes Playwright tests for the requirements and leaves the page empty. In the second session (the Green phase), it builds the page, and the existing tests must pass.

\emph{Agnostic} prompts never mention accessibility. \emph{Oriented} prompts add one sentence that asks for WCAG 2.2 AA and the APG (Fig.~\ref{fig:prompts}). The sentence does not name any technique, such as keyboard support or focus handling, so the agent has to decide what accessibility means for each feature. In \emph{tdd-oriented}, the sentence goes in the Red phase, so the agent must write tests that check accessibility. In \emph{tdd-green-oriented}, it goes in the Green phase, so the agent writes plain feature tests and is asked for accessibility only while building the page. All Red prompts ask for a small test suite so that a very long test suite does not crowd the Green session.

\subsection{Models and runs}

Two models of different cost and reasoning ability ran through the Claude Code command-line agent (version 2.1.309): \emph{Claude Haiku}, a small low-cost model, and \emph{GLM~5.3}, a large reasoning model. Both ran with Claude Code's default reasoning settings, with extended thinking enabled and no effort level set by hand, so each model reasons as much as the agent normally lets it. Each condition ran twice with each model, so the total number of runs is
\begin{equation}
  N = |C| \times |M| \times R = 5 \times 2 \times 2 = 20,
\end{equation}
where $C$ is the set of conditions, $M$ the set of models and $R$ the number of runs per condition and model. Each run is saved as its own git branch, with one commit per session.

\subsection{Running the agent}

Each session runs in a new Docker container that is deleted afterwards. The container only sees a fresh copy of the app. It cannot see the other conditions, the other runs, or the evaluation code. The agent starts with no saved settings, memories, plugins or past chats, and every container has the same tools installed: Node.js, git, Playwright browsers and Claude Code. The agent works on its own, with no human help. When a session ends, a script commits whatever the agent left, and the model, prompts, token usage, time and full transcript are logged.

\subsection{Metrics}

Every finished page is checked against 90 accessibility checks based on WCAG 2.2 AA and the APG, described in Section~\ref{sec:evaluation}. Each check covers one behaviour, for example ``Escape closes the size guide'', and ends as \emph{pass}, \emph{fail} or \emph{skip}. Of the 90 checks, 39 are automated and 51 are done by hand. A check is skipped only when it cannot be judged, and skipped checks are left out of every metric. Each check is also tagged with the WCAG success criterion it tests, or as an APG convention when no criterion applies.

\textbf{Accessibility score.} For a run $r$, let $P_r$ be the number of checks that pass and $F_r$ the number that fail. The score is the share of judged checks that pass:
\begin{equation}
  S_r = 100 \cdot \frac{P_r}{P_r + F_r}.
\end{equation}
The score of a condition $c$ adds up the checks of all its runs before dividing, so every judged check counts the same:
\begin{equation}
  S_c = 100 \cdot \frac{\sum_{r \in c} P_r}{\sum_{r \in c} \left(P_r + F_r\right)}.
\end{equation}
The same formulas over only the automated or only the manual checks give the automated and manual scores.

\textbf{Keyboard task completion.} A run completes the task if a keyboard-only user can buy the shoe: move into the color choices and pick one, open the size list, move through it and pick a size, and type a quantity, without getting trapped. With $T$ the steps of this path and $\mathit{pass}_r(t)$ true when the checks of step $t$ pass,
\begin{equation}
  K_r = \begin{cases} 1 & \text{if } \mathit{pass}_r(t) \text{ for every } t \in T,\\ 0 & \text{otherwise.} \end{cases}
\end{equation}

\textbf{Failed WCAG success criteria.} WCAG judges conformance per success criterion: a criterion fails if any part of the page fails it. With $\mathit{sc}(i)$ the criterion of check $i$ and $\mathcal{F}_r$ the failed checks of run $r$,
\begin{equation}
  W_r = \left|\{\, \mathit{sc}(i) : i \in \mathcal{F}_r,\ \mathit{sc}(i) \neq \mathrm{APG} \,\}\right|.
\end{equation}

\textbf{APG widget conformance.} The page has ten APG widgets, from the breadcrumb to the accordion. A widget conforms when none of its checks fail. With $G$ the set of widgets,
\begin{equation}
  A_r = \left|\{\, g \in G : g \cap \mathcal{F}_r = \emptyset \,\}\right|.
\end{equation}
This counts every widget once, so a widget with many checks, such as the size list, does not dominate the result.

\textbf{Severity-weighted failures.} Not every failure hurts users the same. A failure is a \emph{blocker} (weight 3) when a feature cannot be used by keyboard (WCAG 2.1.1 or 2.1.2), \emph{serious} (weight 2) for any other WCAG failure, and \emph{minor} (weight 1) for a missing APG convention:
\begin{equation}
  D_r = \sum_{i \in \mathcal{F}_r} w(i), \quad w(i) \in \{3, 2, 1\}.
\end{equation}

\textbf{axe miss rate.} The share of failed checks that the axe-core scanner does not report, with $\mathcal{F}^{\mathrm{axe}}_r$ the failed checks that axe covers:
\begin{equation}
  M_c = 100 \cdot \left(1 - \frac{\sum_{r \in c} |\mathcal{F}^{\mathrm{axe}}_r|}{\sum_{r \in c} |\mathcal{F}_r|}\right).
\end{equation}

\textbf{Cost.} For each run, the output tokens $O_r$ and the wall-clock time are reported, together with the score per 10{,}000 output tokens, $E_r = S_r / (O_r / 10^4)$.

\textbf{Comparisons.} With only four runs per condition, significance tests have little power. Each condition score $S_c$ is therefore reported with a 95\% bootstrap confidence interval (10{,}000 resamples of its runs), and each comparison between two conditions $a$ and $b$ with Cliff's delta over the run scores,
\begin{equation}
  \delta = \frac{\left|\{(x, y) : x > y\}\right| - \left|\{(x, y) : x < y\}\right|}{|a| \cdot |b|}, \quad x \in a,\ y \in b,
\end{equation}
which ranges from $-1$ to $1$; values above $0.47$ in absolute value are usually read as a large effect.
