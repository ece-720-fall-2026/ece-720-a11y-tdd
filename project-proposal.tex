\section{Background}

% Problem statement

Web accessibility is a core principle of web development that ensures websites can be used by everyone. 
This is important because the World Health Organization estimates that 1.3 billion people worldwide experience a significant disability~\cite{who2023disability}. 
Despite its importance, web accessibility remains an unsolved problem.
Martins and Duarte found that only 0.5\% of 2.88 million web pages had no automatically detectable accessibility errors~\cite{martins2024accessibility}, which highlights the need for a more systematic approach to web accessibility.

% LLM generated code for web
With the rise of LLMs, one might hope that they could solve these issues by following those rules closely, but this is far from reality.
In a study where developers prompted LLMs to generate websites, Aljedaani et al. reported that 84\% of the resulting websites had accessibility issues~\cite{aljedaani2024chatgpt}.
Related research by Guriță and Vatavu also suggests that although accessibility-oriented prompts reduced violations, semantic accessibility barriers remained~\cite{gurita2025barriers}.
Even though LLMs have been shown to generate more accessible code, they still need to be guided by accessibility rules more strictly.
 
% LLM for TDD
LLMs are used not only to write code, but also to generate tests, and they have been shown to do so with reasonable accuracy.
This has made practices like Test-Driven Development (TDD) easier to implement than ever before.
TDD not only allows for more reliable code, but also provides context for the code written by the LLM.
Mathews and Nagappan found that providing tests during LLM code generation improved functional correctness by 9.15 to 29.57 percentage points~\cite{mathews2024tdd}.
This is a promising approach, but research in this area is still limited, and generating better code while following accessibility rules has not been thoroughly explored.


\section{Planned Approach}

This project will explore the intersection of three topics in software engineering that have been widely studied separately: web accessibility, test-driven development, and large language models.
Our research is based on the following cornerstone hypotheses:
\begin{itemize}
  \item LLMs are trained on large datasets of existing code, which often contain accessibility issues, so they tend to generate inaccessible code.
  \item TDD can help LLMs generate more accessible code by acting not only as a test, but also as a requirement the model must satisfy to pass.
  \item Writing accessibility requirements during the Red phase may guide LLMs to generate more accessible code than writing them during the Green or Refactor phase.
\end{itemize}

To test our hypotheses, we will create a prototype based on an existing example and evaluate how much more accessible code can be generated when we do not specify any rules (baseline), when we specify them before writing tests (red phase), and when we specify them before writing the code (green phase).

For the purpose of this study, we will identify an existing website (e.g., an e-commerce site) and utilise it to develop a 
comprehensive list of requirements, which will be used when generating the code from the LLM. We intend to generate code via 
the LLM in five different ways. These five scenarios enable us to test our hypotheses well [CHANGE SENTENCE] by providing

\section{Planned Evaluation}

The evaluation of the quality of the code, vis-à-vis accessibility, would be conducted through the evaluation of two metrics;
HTML (Static and Runtime) Accessibility Check and Keyboard Accessibility Check. For these two metrics, each scenario's code
would be generated thrice and every rendition of generated code would be tested for the checks mentioned below. As both these
checks require large human reviews, which would be extremely time-consuming, we have limited each scenario's code checks to three.

\subsection{HTML (Static and Runtime) Accessibility Check} 
We intend to utilise two accessibility validators at this stage; eslint-plugin-jsx-a11y and Axe-Core. 
Both of these validators inspect the static HTML for accessibility errors, however, Axe-Core also inspects
the fully rendered DOM. The latter is a critical part of the accessibility check, as this is what an end-user would interact
with. The checks with the two validators would be run independently of each other. The results of the Axe-Core test would 
be segregated into four categories: 

\begin{itemize}
  \item Violations: web elements with definite accessibility errors
  \item Passes: elements that have adhered to WCAG guidelines
  \item Incomplete: elements that stuck to WCAG guidelines but requires human intervention in determining its accuracy.
  \item Inapplicable: all the rules that were skipped as the elements for which they exist are not on the site page.
\end{itemize}

The "inapplicable" results will be omitted as they have no bearing on determining the level of accessibility of the site.
After we review the "incomplete" results, their elements would be categorized under either "violations" or "passes". From 
this categorization, we can highlight the accessibility of the site as a percentage:
\begin{math}
  Axe-Core Accessibility Score (Percentage) = \frac{Violations}{Violations + Passes} \times 100
\end{math}

\subsection{Keyboard Accessibility Check}
Employing Playwright, an open-source automation library, we will check the accessibility
level of the generated site through its responsiveness to simulated keyboard presses. This would
identify how many elements should have been manipulable with a keyboard press and how many actually were. As a score, 
the level of accessibility would be represented by the following formula:

\begin{math}
  Keyboard Accessibility Score (Percentage) = \frac{Successfully Manipulated Elements}{All Manipulable Elements} \times 100
\end{math}

Utilising the scores from above, we would average the accessibility scores for each scenario, and represent the results of 
the averages in the form of a bar graph. The graph would allow us to compare the accessibility scores of our scenarios
and determine if our hypotheses were credible.
